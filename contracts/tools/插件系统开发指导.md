# 面向模型的插件系统：基本开发指导

日期：2026-10-15。本文记录已确认的产品定位、职责边界和开发要求，供后续细化契约与实施时使用。当前仓库已有 Tool 声明格式与示例，尚未实现这里描述的完整插件系统。

## 1. 目标

通过插件给予模型使用某个软件或运用某项技能的能力。作者按公开标准交付插件，主体负责登记、发现、按需加载和调用；接入符合标准的新能力不应要求修改主体的业务代码。

能力不限于具体软件，也可以是分析、写作等任务方法。脚本和 CLI 可以直接作为执行入口，同时兼容 MCP，不要求所有工具先改造成 MCP 服务。

本次保留激活池、海马体与记忆存储设计。QQ 只是能力扩展示例，不是指定集成目标；主体内部记忆、提醒、形象能力是否对外开放，可以单独决定。

## 2. Plugin、Skill、Tool 的关系

| 概念 | 职责 | 应提供的内容 |
| --- | --- | --- |
| Plugin | 安装、分发和管理的单位，组织其包含的能力 | 身份、版本、用途、所含条目的清单及完整内容入口、必要依赖和准备说明 |
| Skill | 指导模型完成某类任务的方法 | 适用场景、输入来源、操作步骤、必要能力依赖、限制、产出和完成标准 |
| Tool | 模型可实际调用的操作能力 | 使用说明、操作列表、参数、调用方式、结果含义、行为影响和运行条件 |

一个 Plugin 可以只包含 Skill、只包含 Tool，也可以同时包含两者。Skill 与 Tool 都是独立可发现、可加载的条目；模型实际选择和使用的是这些条目，不能只给出插件总介绍而隐藏其中的能力。

Tool 可以组织多个相关操作或一个通用 CLI 入口。现有 capability.json 表达的“Tool 能力包”属于这一层，并不等于整个 Plugin。Tool 的 Markdown 使用说明是 Tool 的组成部分，不自动成为一个 Skill。

Skill 不要求自带执行程序，也不强制依赖 Tool。需要外部操作时，引用相应 Tool；随 Skill 提供的可执行操作仍应有明确的 Tool 声明。Tool 可被模型直接使用，不要求先经过 Skill。

例如，一个“文档助手”插件可以提供：

```text
文档助手 Plugin
├── 文档读写 Tool：读取和导出文档的操作、参数及结果约定
└── 周报整理 Skill：组织工作记录、提炼进展、形成周报的方法
```

模型可以直接选择文档读写 Tool，也可以选择周报整理 Skill，再按需要使用文档读写 Tool。上图表达概念归属，不规定安装目录或清单文件名。

## 3. 交付与发现信息

继续采用 JSON 承载结构化声明、Markdown 承载详细说明。Plugin 清单需要能枚举其 Skill 与 Tool，并定位完整内容；不能靠扫描某个 Markdown 文件名来猜测条目类型。

每个可发现条目都应表达以下信息：

| 信息 | 作用 |
| --- | --- |
| 类型 | 区分 Skill 与 Tool，决定如何加载和使用 |
| 稳定身份及来源插件 | 唯一定位条目和依赖，支持定位冲突及版本归属 |
| 名称 | 供模型和使用者阅读 |
| 版本 | 识别内容和约定的变化，不能与声明格式版本混用 |
| 简短描述 | 说明能做什么、何时适合使用及影响选择的主要限制 |
| 完整内容入口 | 选择后取得 Skill 方法或 Tool 定义 |

简短描述以足够选择为准，不塞入全部步骤、参数 Schema 或详细结果结构。例如：

- Tool：“读取指定文档的文本并导出处理结果，适合资料提取与文档输出。”
- Skill：“根据工作记录整理进展、问题和下周计划，适合生成团队周报。”

插件总介绍帮助安装者了解整体用途；条目简短描述帮助模型选择具体能力。实际路径、连接和秘密配置由主体按声明绑定，不让模型通过介绍文字自行编造。

以上是需要表达的信息，不是已经发布的 Plugin 或 Skill JSON 字段表。后续机器格式应分别覆盖插件清单、Skill 条目及统一发现信息；已有 Tool 格式 1 保持明确的适用范围。

## 4. 注册、加载与使用

1. **安装与登记。** 主体读取插件声明，确认条目类型、身份和内容入口，登记轻量目录。登记不运行技能步骤或业务操作，也不要求立刻启动全部工具进程或连接所有服务。
2. **发现与选择。** 模型依据任务和条目简短描述选择 Skill 或 Tool。主体应提供根据身份取得完整内容的途径。
3. **加载 Skill。** 取得方法、限制、输入要求、产出标准和依赖。模型按照方法组织任务；不需要外部操作的 Skill 可以直接用于分析或写作。
4. **加载 Tool。** 需要实际操作时，取得相关 Tool 的使用说明和所需操作定义。Skill 引用了某个 Tool，不代表加载 Skill 时必须一并注入所有依赖详情。
5. **检查条件并执行。** 依据当前定义检查参数和已声明的依赖、配置及连接条件，再按脚本、CLI 或 MCP 约定调用。
6. **解释结果。** 按 Tool 约定区分完成、受理和失败。Skill 再依据自身完成标准判断任务产出，不能把“加载成功”或“请求已受理”直接写成任务完成。

模型可以跳过 Skill 直接选择 Tool。上述过程是使用行为要求，不指定线程、类、缓存结构、加载请求的函数名或上下文淘汰算法。

“已安装”“声明符合标准”“详细内容已加载”“当前可执行”“任务已完成”各自回答不同的问题。实现中应能清楚报告当前事实，不能用一个模糊的 available 或 success 代替全部含义。

## 5. 依赖、版本和管理边界

Skill 需要特定 Tool 时，应引用可唯一识别的条目；依赖特定操作时，要能对应到该 Tool 的公开操作。显示名称不足以作为唯一引用，Skill 也不应复制另一份执行绑定来替代 Tool 的声明。

允许选择替代工具的方法，应说明所需能力与选择条件。选定后仍需加载并遵循实际 Tool 定义，不能仅因名称相似就认定两个工具等价。

缺少依赖、版本含义不匹配、参数定义尚未取得或运行条件未满足时，报告具体原因。动态候选值由相关 Tool 说明获取来源；固定参数 Tool 无须额外实现动态查询。

插件安装不代表其依赖的软件已经安装或账户已登录。准入声明检查与当前就绪情况分别报告，不要求通过执行有副作用的业务操作来证明声明合格。

安装、更新、启用、禁用和卸载围绕 Plugin 归属管理其条目。禁用或卸载后不能继续接受该插件的新调用；更新后不能让旧详情被当作新版本的定义。正在执行的操作、缓存和资源如何收尾，需要在相应实现前明确，不能默认重放未确认结果的操作。

## 6. 主体与提供者分别负责什么

| 提供者 | 主体 |
| --- | --- |
| 声明 Plugin 组成、Skill 方法和 Tool 操作 | 解析与校验声明，登记可发现目录 |
| 写清适用场景、行为影响、运行条件和依赖 | 提供按需加载内容与取得依赖的途径 |
| 提供或明确如何取得实际执行入口 | 按公开调用约定绑定配置、校验参数和执行 |
| 解释结果与任务完成标准 | 保留结果含义，报告缺项、冲突及当前就绪情况 |
| 通过公开约定接入，不依赖主体内部对象 | 通过通用契约接入新插件，避免按具体软件名称添加业务分支 |

宿主对 JSON Schema 的支持范围和不支持时的处理，应在参数校验实现前明确；不能静默忽略约束。现有内部工具可保留在其原有职责内，是否改成外部条目应按需要决定。

## 7. 后续开发顺序与验收要求

先补齐 Plugin 与 Skill 的机器声明及示例，再实现目录和加载链路，随后接入执行与管理行为。每一步都应有可独立检查的交付物：

| 工作 | 交付物与最低验收 |
| --- | --- |
| 声明格式 | Plugin 组成、Skill 方法入口、两类条目发现信息、引用和版本规则有明确格式；纯 Skill、纯 Tool、混合插件均可表达；不将纯 Skill 按缺少 operations 拒绝 |
| 注册与发现 | 添加符合契约的新插件无需修改主体业务代码；目录能区分条目类型和归属；身份冲突或断裂引用被明确报告 |
| 按需加载 | 启动时不全量注入技能正文和工具参数；选择后取得正确内容；加载 Skill 不执行操作，依赖 Tool 详情按实际需要取得 |
| 操作执行 | 用本地脚本、CLI 和 MCP 分别验证调用约定；参数非法、依赖缺失、连接失败、工具错误能准确报告；受理与完成不混淆 |
| 插件管理 | 更新、禁用和卸载后，目录、依赖关系及后续调用与管理结果一致；进行中的操作按事先明确的规则处理 |

验收应同时保留“模型直接使用 Tool”和“模型加载 Skill 后按需使用 Tool”两条路径，并覆盖不依赖工具的纯 Skill。测试使用可控样例和临时数据，不把真实软件的未知状态当成契约本身的结论。

这份指导不冻结内部系统设计。开始对应实现前，还需要完成 Plugin/Skill 清单字段、身份引用与版本规则、加载请求表达、管理时正在运行任务的处理等具体约定；不能从本文中的概念示例推断出已经存在的协议。
