# Skill 与 Tool 分类及按需加载约定

日期：2026-10-15。依据：为模型提供使用软件或运用技能的能力；Skill 与 Tool 分开定义，两者都具备简短描述并按需加载。本附件规定外部交付和使用约定，不指定加载器、缓存或调用接口的实现。

## 1. 两类条目的职责

| 类型 | 提供的能力 | 完整内容 | 如何使用 |
| --- | --- | --- | --- |
| Tool | 实际执行某项操作，例如读取文件、搜索、操作软件 | 使用说明、操作列表、参数、调用绑定、结果及环境要求 | 模型按操作定义发起调用，执行入口可以是脚本、CLI 或 MCP |
| Skill | 指导模型完成某类任务，例如整理周报、分析资料 | 适用场景、方法步骤、输入来源、必要的能力依赖、产出及完成标准 | 模型读取说明并遵循方法；需要外部操作时使用相应 Tool |

Tool 可以包含多个相关操作或一个通用入口，沿用已有契约。Tool 自身仍需提供使用说明，说明文件的存在不使它自动成为 Skill。

Skill 不要求自带可执行程序，也不强制依赖 Tool；只用当前材料进行分析或写作的方法也可以是 Skill。Tool 可以独立被选择和调用，不要求先加载某个 Skill。

Plugin 是安装、分发和管理单位，可以只提供 Skill、只提供 Tool，也可以同时提供两者；整体要求见 [插件系统开发指导](./插件系统开发指导.md)。其下两类条目必须有可区分的身份、类型和完整内容入口，能够分别被发现和加载。Skill 中若附带需要实际执行的操作，应作为 Tool 明确声明，再由 Skill 引用；不能通过技能文字绕过调用约定。

本附件不要求把所有 Skill 与 Tool 分成不同安装包，也不增加 MCP 强制包装要求。

## 2. 简短描述用于选择

两类条目都应提供唯一可区分的身份、类型、名称、版本、简短描述和完整内容入口。身份、版本和入口用于准确定位；简短描述应让模型判断是否适合当前任务。

| 条目 | 简短描述示例 |
| --- | --- |
| Tool：文档读取 | 读取指定文件的文本，适合从本地资料中提取待分析内容。 |
| Skill：周报整理 | 根据工作记录整理进展、问题和下周计划，适合生成面向团队的周报。 |

描述至少说明“提供什么”和“适合什么时候使用”；影响选择的重要限制也应简述。不能只写“通用助手”“强大工具”之类无法区分用途的文字。

简短描述不承载完整步骤、全部参数 Schema、详细返回字段或实际配置值。当前可用性由主体根据已知运行条件报告，不能由作者一句“可用”代替核实；尚未检查可以明确表示未知。

这里规定目录必须表达的信息。现有 Tool 格式 1 的身份与摘要字段继续有效；Skill 清单以及统一目录的具体机器字段不由本附件自动新增，后续细化时应保持两类条目明确可分。

## 3. 按需加载的行为约定

1. **启动登记。** 主体登记条目类型、身份、简短描述和完整内容入口，形成可供模型发现的目录。登记不等于把所有正文与操作定义放进模型上下文，也不要求立即启动全部程序或连接全部服务。
2. **按任务选择。** 模型根据任务及简短描述选择相关 Skill 或 Tool；主体提供按条目身份取得完整内容的途径。
3. **加载 Skill。** 读取选中 Skill 的完整方法、限制、产出要求与依赖。加载说明不等于执行它涉及的操作。
4. **加载 Tool。** 在需要使用某个 Tool 时，取得它的完整使用说明和所需操作定义，使模型知道准确参数和返回含义；调用绑定及实际配置由主体解析。
5. **执行与解释。** 确认所需定义和运行条件后执行 Tool，并按其结果约定解释。需要其他能力时再继续发现和加载。

模型可以直接从目录选择 Tool；使用不依赖外部操作的 Skill 时，也可以在读完说明后直接完成任务。这不是要求每次任务都经过固定的 Skill → Tool 步骤。

Skill 引用某个 Tool，不意味着加载 Skill 时就把该 Tool 的所有定义以及其他关联内容一次性注入上下文。依赖的详细定义在实际需要时取得；加载策略应保留这种区分。

是否使用工具调用表达加载请求、如何缓存、何时移出上下文，属于后续实现选择。本契约要求主体能够支持选择后取得内容，不在这里规定内部协议。

## 4. Skill 如何引用 Tool

需要特定 Tool 时，Skill 应明确引用可识别的 Tool 身份；需要特定操作时，应能对应到该 Tool 中的操作，不能只给出一个含糊的展示名称。影响步骤正确性的兼容条件和参数来源也需说明。

Skill 中的示例辅助理解，实际调用仍以当前 Tool 的公开定义为准。Skill 不应复制并维护另一份脱离 Tool 的执行绑定，也不能凭文字指定任意未注册程序。动作候选等动态值从 Tool 声明的来源或查询操作取得。

只需要某类能力、允许选择替代 Tool 时，应说明所需能力和选择条件；不能假设主体能够自动将任意两个 Tool 判为等价。选择后仍需加载并遵循该 Tool 的实际定义。

缺少所需 Tool、参数定义不明确或运行条件未满足时，应报告具体缺项。不能为了让 Skill 看似执行成功而编造调用或结果。依赖暂时未就绪与 Skill 本身的说明是否完整分别判断。

## 5. 分类后的准入判断

| 检查内容 | Tool | Skill |
| --- | --- | --- |
| 能否发现与选择 | 类型、身份、简短用途和完整定义入口明确 | 类型、身份、简短用途和完整说明入口明确 |
| 能否正确使用 | 操作、参数、执行入口和前置条件明确 | 方法、步骤、输入来源、限制和必要依赖明确 |
| 能否判断结果 | 成功、失败、受理及业务结果含义明确 | 产出和完成标准明确；调用 Tool 的结果按该 Tool 约定解释 |
| 能否独立接入 | 通过公开约定调用，不依赖主体内部实现 | 通过公开能力引用组织任务，不依赖主体内部对象 |

纯 Skill 不因缺少可执行入口被拒绝；只有目标口号、缺少实际方法和完成标准的说明，也不能仅凭文件名认定为合格 Skill。

## 6. 与已有文档的关系

现有 [能力包声明模板](./能力包声明模板.md)、[capability.schema.json](./capability.schema.json) 及三个作者示例描述的是 Tool 能力包。其 operations 非空要求继续适用于 Tool，不能用来拒绝纯 Skill。

现有 62 项自动验证覆盖 Tool 格式及有限的临时数据执行，不覆盖 Skill 清单或分类后的按需加载运行行为。项目内部的 SkillStore 保存学习得到的工作流，不能仅因同名就视为已经实现本附件的外部 Skill 注册与加载。

对记忆、提醒、形象等主体能力的内部耦合核对可以作为现状记录；它们是否开放不再列为这份外部 Skill/Tool 准入契约的前置要求。
