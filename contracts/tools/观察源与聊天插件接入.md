# 观察源与聊天插件接入

聊天插件沿用现有 Tool 的发现、加载和调用契约。主体通过工具主动查看消息；需要持续接收消息时，插件再声明可选的 source。接收消息只归档事实，是否交流由活动选择、当前权限和预算共同决定。

完整可运行示例见 [controlled-chat](./examples/controlled-chat/README.md)，工程边界见[主设计 §3.9](../agent/自主Agent-身份记忆与活动运行时-桌面端系分.md#39-外部观察与-qq-式自主使用验证)。真实 QQ 适配器需要自行实现账号连接或桌面操作，并返回实际结果；当前示例使用本地 SQLite 消息日志，没有登录 QQ。

## 插件交付

| 文件 | 用途 |
| --- | --- |
| plugin.json | 声明 Tool 条目和可选 sources；具体软件名称不进入主体代码 |
| tool.json、USAGE.md | 定义读取、发送、核对结果等操作及使用方法 |
| 实际适配器 | 实现后端调用或桌面操作，维护稳定消息 ID；需要时持久化来源序列 |
| source.json（可选） | 声明 agent-observation-1 流协议、配置和固定 command 参数 |

source 声明使用 [source.schema.json](./source.schema.json)，示例见 [source.json](./examples/controlled-chat/source.json)。程序、脚本路径和连接配置由宿主提供；source 不接受模型拼接的启动命令。清单引用必须在包内，程序路径由宿主精确授权。日志、数据库等可变文件放在包外，避免改变插件内容摘要。

只有主动查询的插件可以完全不声明 sources。

## 宿主绑定

在角色运行目录的 plugins.json 中配置以下字段。安装、能力授权与自主开关的完整说明见[插件运行时接入](./插件运行时接入.md)。

| 字段 | 作用 |
| --- | --- |
| observationBindings | 将插件绑定到确定的账号连接、自身身份及允许读取的会话 |
| observationAdapters | 将某个准确 CapabilityRef 的真实查询结果映射为消息 |
| replyBindings | 将真实发送参数和回执绑定到确定的外部会话 |
| configuration | 按 Tool entryId 或 source.configurationKey 提供执行配置 |
| grants | 分别授权内部主动查询和具体外部会话的操作；autonomous 控制自主调用 |

observationBindings 的一项示例：

```json
{
  "id": "account",
  "pluginId": "example.controlled-chat-plugin",
  "channel": "controlled-chat",
  "connectionKey": "account-one",
  "provider": "controlled-chat",
  "namespace": "account-one",
  "selfIdentity": {
    "provider": "controlled-chat",
    "namespace": "account-one",
    "remoteActorId": "pet-account"
  },
  "conversations": [{"remoteConversationId": "group-a", "kind": "group"}],
  "source": {
    "sourceId": "example.controlled-events",
    "configurationKey": "example.controlled-events",
    "executor": "/absolute/path/python3",
    "enabled": false
  }
}
```

source 子项可省略。enabled 默认关闭；启用 source 只打开消息归档入口，不自动开启自主交流。更换账号须更新 connectionKey、namespace 和 selfIdentity，不能仅替换昵称。收到的消息不能自行添加允许会话或把某人认作主人。

查询映射通过完整的 pluginId、entryId、entryVersion、operationId 绑定。itemsPointer 指向结果数组，fields 使用 JSON Pointer：

```json
{
  "ref": {
    "pluginId": "example.controlled-chat-plugin",
    "entryId": "example.controlled-chat",
    "entryVersion": "1.0.0",
    "operationId": "read"
  },
  "observationBindingId": "account",
  "itemsPointer": "/items",
  "fields": {
    "eventId": "/event_id",
    "sequence": "/sequence",
    "cursor": "/cursor",
    "remoteConversationId": "/chat_id",
    "remoteMessageId": "/message_id",
    "text": "/text",
    "remoteActorId": "/speaker_id",
    "occurredAt": "/occurred_at",
    "replyToRemoteId": "/reply_to"
  }
}
```

必填映射为 eventId、sequence、cursor、remoteConversationId、remoteMessageId、text。speakerDisplayName、remoteActorId、occurredAt、replyToRemoteId、historicalImport 可选。只有实际 completed 结果进入归一化；日志、模型陈述、status、accepted 和 unknown 不构成消息事实。每批最多 256 条，较多结果须分页，空数组表示本次查询没有消息。

## source 流协议

source 使用独立 command 进程，通过 UTF-8 JSONL 双向通信。普通 Tool 的 stdout 仍是单个 JSON 结果。

宿主向 stdin 发送：

```jsonl
{"type":"start","cursor":""}
{"type":"ack","eventId":"event-1","cursor":"cursor:1"}
{"type":"stop"}
```

首次 start 的 cursor 为空，重连时使用上次已提交的监听游标。source 向 stdout 发送消息或 status；诊断写 stderr。消息示例：

```json
{
  "type": "observation",
  "kind": "message",
  "eventId": "event-1",
  "sequence": "1",
  "cursor": "cursor:1",
  "occurredAt": "2026-10-17T00:00:00.000Z",
  "conversation": {"remoteConversationId": "group-a", "kind": "group"},
  "speaker": {"provider": "controlled-chat", "namespace": "account-one", "remoteActorId": "alice"},
  "message": {"remoteMessageId": "message-1", "text": "第一章看完了。"}
}
```

同一事件重放时 eventId、sequence 和 cursor 保持稳定。sequence 是规范的正十进制字符串，上限 9223372036854775807；cursor 是适配器自己的不透明值。源必须从宿主已提交游标有序重放，不能仅按“最近看到的消息”生成临时 ID。平台没有序列时，适配器需提供持久日志。

单行上限为 64 KiB，消息正文上限为 8000 个 UTF-16 code unit，待归档队列最多 256 条。错误或超限进入补拉状态，不能截断正文后当作完整消息。只有消息、来源、待处理线索和监听水位同事务提交后才 ack；失败不能跳过该事实再确认后续水位。重连使用已提交 cursor。

查询和 source 共用消息与事件 ID，但查询可能只覆盖一个群或某一页，因此**查询不推进账号的监听游标**。宿主内部区分 Query 和 Source，插件不能在消息载荷中设置该字段。查询分页使用真实结果 cursor；Source 有序流才推进监听水位。先查到群 A 的序号 2，再启用 source，群 B 尚未读取的序号 1 仍会重放。

没有原始时间时省略 occurredAt，宿主保存未知原始时间和独立 receivedAt；不要用抓取时刻冒充发言时间。缺少稳定发言人 ID 时保留未知人物，不填主人。自身回显按已核验 selfIdentity 去重，historicalImport=true 的补录不会触发自主回复。

## 发送、等待与退出

发送沿用 replyBindings。宿主先固定会话和调用身份，再执行实际能力；真实回执必须提供远端消息 ID、实际正文和发生时间。服务端调整后的正文按实际值归档。只生成正文、返回 accepted 或结果未知，都不等于发送成功。

已经准备的会话回复沿用原派发记录。接口没有原生引用回复功能时，可以只映射 content 和 remoteConversationId，宿主仍保留原消息引用。归档失败会保留回执并阻止继续发送，恢复时补归档，不重新发送。

成功发送后，任务规划可以提出：

```json
{"wait":{"kind":"message","afterStepId":"本活动实际成功步骤的ID","reason":"等对方回复"}}
```

wait 与工具调用、完成候选和用户问题互斥。宿主从已归档动作取得真正的 outgoing 消息锚点，等待时释放前台；匹配回复到达后，在安全边界保存当前活动，再由选择流程恢复。普通消息不会自动打断阅读。用户暂停和重启暂停保留原来的恢复权限。

禁用、切换角色或退役后停止新启动与重连。已经接收到的事实和已发送回执仍归原角色库，不能借此触发新角色活动。真实 QQ 接入验收还需记录所用后端、账号类型、支持操作及实际发送回执；受控示例通过不能代替这一步。
