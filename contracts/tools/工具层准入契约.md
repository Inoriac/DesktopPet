# Skill 与 Tool 准入契约

日期：2026-10-15。

状态：本文整理已确认的准入原则，作为能力提供者与项目主体之间的共同标准。根据能力定位，区分 Skill 与 Tool，并分别提供简短描述和按需加载内容。现有 JSON 清单＋Markdown 模板描述 Tool；Skill 的机器格式需按分类约定继续细化。内部实现另行制定。

## 1. 目的与范围

本契约面向给予模型使用某个软件或运用某项技能的能力。Tool 提供可执行的操作，Skill 提供完成任务的方法；主体依据公开声明让模型发现、按需加载和使用它们，无需了解提供者的内部实现。

主体内部的记忆、提醒、形象能力是否对外开放，可以单独讨论，不构成本契约成立的前置条件。

本次保留现有激活池、海马体和记忆存储设计。QQ 仅是可扩展能力的举例，不是本契约的专用模块或业务需求。

## 2. 准入单位与类型

Plugin 是安装、分发和管理单位，可以包含 Skill、Tool 或两者。主体登记插件的组成，并让其中的条目分别被模型发现和按需加载。整体开发要求见 [插件系统开发指导](./插件系统开发指导.md)。

能力条目必须区分 Skill 与 Tool，不能因为两者都有说明文件就混为一种。Skill 提供完整方法、输入来源、必要依赖和产出要求，可以复用已有 Tool，也可以不依赖 Tool。

Tool 能力包由一份使用说明和一组相关的可调用操作组成，属于插件内的 Tool 层，不代表整个 Plugin。以下操作粒度及接入方式的约定适用于 Tool。

能力包可以包含：

- 多个具体操作，例如读取、搜索、导出。
- 通用调用入口，例如由模型根据说明组织命令参数的 CLI 入口。
- 上述两种方式的组合。

契约不限制操作粒度。通用入口仍须明确可用命令范围、参数组织方式和结果含义，不能只提供一个没有使用约定的执行入口。

脚本、CLI 和 MCP 均可作为接入方式，不要求所有工具先包装为 MCP 服务。

## 3. 两层信息

| 层次 | 能力包必须提供的内容 | 用途 |
| --- | --- | --- |
| 注册信息 | 类型、唯一可区分的标识、名称、版本、简短用途，以及完整内容入口 | 启动时登记，供模型发现和选择，不提前注入全部正文和参数 |
| Tool 完整定义 | 使用说明、操作列表、调用方式、参数与结果说明、必要的环境和配置 | 需要使用该 Tool 时加载，使模型和主体能够准确调用 |
| Skill 完整说明 | 适用场景、方法步骤、输入来源、必要依赖、产出与完成标准 | 需要使用该 Skill 时加载；依赖 Tool 的完整定义按实际需要另行取得 |

使用说明可以自由编写。Tool 的调用入口与调用规则必须明确，Skill 的方法与依赖必须明确。JSON 清单承载结构化声明、Markdown 承载详细说明；现有格式附件覆盖 Tool。分类、简短描述和加载行为见 [分类及按需加载约定](./Skill与Tool分类及按需加载约定.md)。

## 4. 最低准入要求

### 4.1 能够被发现

提供稳定且可区分的身份信息、简短用途和完整定义入口。主体无需阅读全部操作说明，就能向模型展示包的用途并定位详细内容。

### 4.2 能够被理解

说明适用场景、操作流程、前置条件、限制及必要的使用示例。对于可能修改文件、发送内容或改变其他状态的操作，应说明其行为影响。

### 4.3 能够被正确使用

Tool 明确每项操作的名称、用途、实际执行入口和参数约定，包括必要参数及其含义。通用 CLI 入口同样需要说明如何组织命令与参数。

作为 Tool，只提供说明而没有可执行操作入口，或只提供脚本而没有调用规则，均不满足此项要求。作为 Skill，不要求自带执行入口，但必须提供可遵循的方法、输入来源和必要依赖，不能只写功能介绍。

### 4.4 结果能够被判断

明确操作返回什么，以及成功、失败和仅受理分别表示什么。

Skill 应明确任务产出和完成标准；其中调用 Tool 的结果仍按相应 Tool 的约定解释，不能把说明加载完成当作任务完成。

如果操作只负责提交请求，结果必须能够与实际业务完成区分。失败时应提供足以理解失败原因的信息，不能让主体通过猜测判断结果。

### 4.5 运行条件明确

说明所需依赖、配置、登录或授权条件，以及使用者如何满足这些条件。工具当前能否运行，与其声明是否符合准入标准分开判断。

此项要求明确条件，不强制所有能力包提供同一种自动探测或安装机制。

### 4.6 不依赖主体内部实现

工具的业务逻辑不直接依赖项目内部类、数据库表或窗口对象。需要主体提供的能力时，通过公开契约交互。

主体和工具提供者依赖共同约定，而不是互相了解内部代码。接入一个符合既有公开契约的业务工具，不应要求修改主体的业务逻辑。

## 5. 主体的责任

作为契约的另一方，主体应当：

1. 启动时登记 Skill 与 Tool 的类型、身份、简短描述和完整内容入口，使模型能够发现它们。
2. 根据选择按需加载 Skill 方法或 Tool 定义，Skill 依赖的 Tool 也按实际需要加载，不因注册而全量注入上下文。
3. 支持模型遵循 Skill 方法，并按 Tool 声明的方式、参数及前置条件调用，不要求作者针对不同任务修改主体代码。
4. 如实保留结果含义，不把“已经受理”解释成“已经完成”。
5. 区分准入情况与当前可用性，能够说明缺少依赖、配置、登录或授权等原因。

## 6. 准入合格与当前可用分开判断

准入检查关注：契约信息是否完整、明确且可遵循。

运行检查关注：当前环境和条件是否足以执行。

| 情况 | 判断 |
| --- | --- |
| 声明完整、调用明确，但尚未安装所需 CLI | 可以通过准入；当前缺少依赖 |
| MCP 服务暂时离线，或外部系统尚未登录 | 可以通过准入；当前不可用，应说明原因 |
| 脚本能运行，但缺少参数或结果说明 | 不满足准入标准，需补齐调用约定 |
| 声明为 Tool，但只有功能介绍，没有实际操作入口 | 不满足 Tool 准入标准，需提供操作实现及调用方式 |
| 声明为 Skill，有完整方法、必要依赖和完成标准，但不自带执行程序 | 可以满足 Skill 准入标准，依赖是否就绪另行判断 |
| 提供通用 CLI 入口，命令范围、参数与结果含义明确 | 可以满足准入标准，不必逐项拆成细粒度工具 |

## 7. 准入核对清单

- 能否凭注册信息区分并发现这个能力包？
- 能否定位完整定义，并理解何时、如何使用？
- Tool 能否依据声明准确调用操作；Skill 能否依据说明组织并完成任务？
- 能否依据约定解释 Tool 结果，区分成功、失败与受理，并判断 Skill 产出是否达标？
- 是否说清运行所需条件，以及如何满足这些条件？
- 是否通过公开契约交互，而不依赖主体内部实现？

以上均满足，说明能力包符合最低准入标准；能否立即执行，再按当前运行条件判断。

后续对契约表达格式的细化及工具层解耦，应以本文为准入基线。本文不规定内部类、线程、缓存、数据库、执行调度或具体权限实现。

格式附件见 [能力包声明模板与填写规则](./能力包声明模板.md)。[准入检查规则与示例核对](./准入检查规则与示例核对.md) 及 [机器检查 Schema](./capability.schema.json) 用于核对这些约定，不涉及主体内部实现。

现有实现与验证范围见 [现有工具契约适配验证](./现有工具契约适配验证.md)。内部工具不要求全部改为外部能力包；Plugin/Skill 清单和宿主加载另有对应 Schema 与运行时测试，不能只凭 Tool 声明验证推断所有集成行为。
