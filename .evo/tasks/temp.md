**1. 多线程与事件循环：为什么调用模型、读取数据库时，桌宠还能继续动？**

对应实现：[chat_preparation_executor.cpp](/Users/huang/Desktop/DesktopPet/core/ai/chat/chat_preparation_executor.cpp)、[ai_brain.cpp](/Users/huang/Desktop/DesktopPet/core/ai/ai_brain.cpp:632)。

当前聊天链路分阶段执行：

- GUI 线程处理输入、发布待回复消息、维护对话状态。
- 准备线程读取人格和记忆，构建上下文。
- 网络请求通过 Qt 的异步机制完成。
- 副作用线程处理事件、记忆写入和日志。

能关联的八股：**进程与线程、事件循环、同步与异步、阻塞与非阻塞、线程通信、线程亲和性。**

这里很适合讲清楚一个基础概念：**异步不等于多线程。** 网络请求可以靠事件循环异步等待，而记忆检索、上下文构建等工作通过独立线程避免占用 GUI。

面试官容易追问：

- 为什么不能在线程里直接更新界面？
- `QThread` 对象与它管理的线程有什么区别？
- `DirectConnection` 和 `QueuedConnection` 分别在哪个线程执行？
- 为什么 SQLite 连接要在使用它的线程创建和释放？
- 把任务放到工作线程以后，就一定不卡了吗？

最后一问能讲出深度：还要考虑主线程回调耗时、锁竞争、队列积压和关闭时的等待。当前普通聊天中的部分工具仍由状态机同步调用，因此不能笼统宣称“所有工具执行都已异步化”。

**2. 并发正确性：取消请求后，旧回复为什么不会覆盖新回复？**

对应实现：[ai_brain.cpp](/Users/huang/Desktop/DesktopPet/core/ai/ai_brain.cpp:632)。

准备结果回来时，代码会检查当前响应是否结束，以及 `requestId`、`generation` 是否仍匹配。

可以用一个具体场景讲：

> 用户发出请求 A，随后取消并发出请求 B。A 的后台工作可能已经接近完成，取消无法保证它立即消失。如果只看“回调成功”，A 就可能被显示到 B 的会话中，所以结果必须通过请求身份和代次校验。

能关联的八股：**竞态条件、逻辑取消、原子变量、内存可见性、过期结果隔离。**

值得准备的追问：

- 已经调用 `abort()`，为什么还需要校验代次？
- `requestId` 和 `generation` 各解决什么问题？
- 为什么一个 `bool cancelled` 有时不够用？
- `std::atomic` 能不能让整个业务流程自动线程安全？
- `memory_order_acquire/release` 保证什么？

这部分特别适合体现工程判断：取消底层操作和拒绝过期结果，是两道不同的保障。

**3. 生产者消费者与背压：用户发得快、磁盘写得慢怎么办？**

对应实现：[chat_side_effect_queue.cpp](/Users/huang/Desktop/DesktopPet/core/ai/chat/chat_side_effect_queue.cpp:440)。

项目有一个默认容量为 256 的副作用队列，用来提交事件、记忆强化、用户记忆和日志。队列用互斥锁保护，工作线程取出任务后，在锁外执行持久化。

当前还做了几个具体取舍：

- 队列满时优先丢弃非关键日志。
- 为会话结束的 barrier 预留容量。
- 关键工作无法入队时明确返回失败。
- 关闭时支持排空已接受任务。

能关联的八股：**生产者消费者、有界队列、互斥锁、临界区、背压、过载保护、优雅关闭。**

面试时可以重点讲：

> 为什么不使用无界队列？因为消费者持续落后时，无界队列只是把过载变成内存增长和越来越长的处理延迟。

还有两个容易被问住的细节：

- **这里的 barrier 是队列中的顺序标记**，用于确认前面的工作已经处理到相应阶段；它和 CPU 内存屏障不是同一概念。
- **这是进程内队列**，不能直接把它说成具备断电恢复能力的持久消息队列。

**4. 数据库事务、锁与索引：SQLite 也能讲得很深**

对应实现：[sqlite_memory_repository.cpp](/Users/huang/Desktop/DesktopPet/core/ai/memory/sqlite_memory_repository.cpp:116)、[sqlite_event_repository.cpp](/Users/huang/Desktop/DesktopPet/core/ai/event/sqlite_event_repository.cpp:431)。

项目中实际用到了：

- WAL 模式与 `busy_timeout`。
- 多线程各自持有数据库连接。
- 用唯一命名的 `SAVEPOINT` 支持嵌套事务。
- 用预期序号更新 consumer checkpoint。
- 为记忆、标签、关系、待处理任务等建立索引。

能关联的八股：**ACID、事务隔离、读写并发、锁竞争、乐观并发控制、联合索引、查询计划。**

这里有两个很好的项目案例。

第一，外层整理事务调用了内部也需要事务的存储操作。内部“提交”只能释放自己的保存点，不能把外层一起提交；外层失败时，还应能整体回滚。

第二，checkpoint 更新带上预期值：

```sql
UPDATE consumer_checkpoint
SET last_sequence = ?
WHERE consumer_id = ? AND last_sequence = ?;
```

这可以关联到**数据库中的比较并更新、版本冲突和丢失更新**。

建议重点准备这些问题：

- WAL 为什么能改善读写并发？为什么仍不能支持多个写事务同时写入？
- `busy_timeout` 能否解决所有并发冲突？
- 保存点和真正的事务提交有什么区别？
- 联合索引的列顺序怎样根据查询条件决定？
- 为什么给所有字段建索引会有问题？

讲索引时要分清数据库实现，别把 MySQL/InnoDB 的索引结构和隔离级别细节直接套到 SQLite 上。

**5. Outbox、幂等与最终一致性：一次操作涉及多份数据怎么办？**

对应实现：[event_outbox.cpp](/Users/huang/Desktop/DesktopPet/core/ai/event/event_outbox.cpp)、[memory_index_worker.cpp](/Users/huang/Desktop/DesktopPet/core/ai/memory/memory_index_worker.cpp)。

**8. 数据结构与算法：记忆系统可以讲成一条完整检索链路**

对应实现：[memory_retriever.cpp](/Users/huang/Desktop/DesktopPet/core/ai/memory/memory_retriever.cpp)、[memory_keyword_index.cpp](/Users/huang/Desktop/DesktopPet/core/ai/memory/memory_keyword_index.cpp)、[associative_activation_engine.cpp](/Users/huang/Desktop/DesktopPet/core/ai/memory/associative_activation_engine.cpp)。

当前实现的主线是：

> 激活池、待整理记忆工作集、可选向量索引、关键词/标签四路采集种子 → 校验与去重 → 最多保留 16 个种子 → 有限图传播 → ACT-R 精排 → 输出相关记忆。

其中关键词使用内存倒排表，语义标签还会查询 SQLite，词法 token 和持久化语义标签是分开的；准备线程长期持有缓存，并按内容、资格等修订变化刷新。最终候选还会重新检查有效性。

能关联的八股：

- **哈希表与集合**：去重、候选合并。
- **倒排索引**：词到记忆 ID 的映射。
- **优先队列**：图传播优先处理较强信号。
- **图遍历**：环路、跳数、邻居数和候选预算。
- **近似最近邻**：HNSW 的准确率、延迟和空间取舍。
- **缓存一致性**：什么时候复用，什么时候失效。

很好的追问包括：

- 为什么不能每次遍历全部历史记忆？
- 为什么多个通道命中，不能简单重复加分？
- 图里存在环会怎样？
- 为什么传播有跳数和候选数限制？
- HNSW 为什么是近似查询？删除和更新有什么复杂性？

当前主路径是**多路种子加图传播，再由 ACT-R 排序**。README 中规划的 RRF 不应讲成已经落地的融合算法。

**9. 状态机与故障恢复：任务中断以后，能不能直接继续？**

对应实现：[task_orchestrator.cpp](/Users/huang/Desktop/DesktopPet/core/ai/task/task_orchestrator.cpp:123)。

复杂任务具备检查点、调用次数与时间预算、暂停恢复、取消代次和重启恢复逻辑。

最值得讲的是这个场景：

> 工具已经创建了一个提醒，但程序还没保存执行结果就崩溃。重启后，系统只能知道这个动作已派发，无法确定是否成功。如果直接重放，可能创建两个提醒。

当前实现会把这类有副作用且结果不明的动作标为 `unknown`，恢复后要求核对。

能关联的八股：**有限状态机、持久化检查点、至少一次与至多一次执行、幂等、故障恢复、单调时钟。**

- 为什么等待用户的时间不应算活跃执行时间？
