# 能力包声明模板与填写规则

日期：2026-10-15。状态：使用者已确认继续，以本模板作为准入契约的格式附件；当前补充检查规则与示例核对。

依据：[工具层准入契约](./工具层准入契约.md)。本附件定义工具提供者填写的文件、字段与调用表达，不从已撤回的系分草稿继承内部设计。

## 1. 工具提供者交付什么

采用 **JSON 清单＋Markdown 使用说明**，具体组织为：

- `capability.json`：包的注册信息，以及完整定义所在的 `definition` 对象。
- `USAGE.md`：适用场景、操作流程、前置条件、结果解释和使用示例。
- 实际操作实现：可以是随包提供的脚本，也可以是使用者已有的 CLI 或 MCP 服务。实现不必与声明放在同一目录，但必须明确如何取得、配置和调用。

两层信息是逻辑上的分层：注册使用清单顶层的身份和摘要，完整定义入口固定为 `capability.json#/definition`。完整说明和操作定义在需要使用时加载。本格式不要求为两层信息分别维护两份 JSON。

本文只规定工具提供者如何声明，不规定主体内部如何注册、存储、调度或执行。

## 2. 注册信息

| 字段 | 是否必填 | 如何填写 |
| --- | --- | --- |
| formatVersion | 是 | 声明格式版本，本格式使用字符串 `1`；与包版本分开 |
| id | 是 | 稳定的包标识，例如 `example.text`，不使用展示名称代替 |
| name | 是 | 给使用者和模型看的名称 |
| version | 是 | 包自身版本，例如 `1.0.0`；接口含义变化时更新 |
| summary | 是 | 简短说明能做什么、适合什么任务，供发现能力 |
| definition | 是 | 完整定义对象，见下一节 |

本格式中的包和操作标识使用小写英文字母、数字、点、下划线或连字符，首字符为字母。包标识在注册范围内唯一，操作标识在包内唯一。文档引用操作时使用 `包标识/操作标识`，例如 `example.text/count`。

## 3. 完整定义

| 字段 | 是否必填 | 如何填写 |
| --- | --- | --- |
| instructions | 是 | Markdown 主说明的相对路径，例如 `USAGE.md` |
| requirements | 是，可为空数组 | 运行条件列表，每项包含 `id`、`description`、`setup`；说明需要什么、如何满足 |
| configuration | 是，可为空数组 | 使用者需填写的设置，每项包含 `key`、`description`、`kind`、`required` |
| operations | 是，至少一项 | 具体操作或通用入口，见下一节 |

configuration.kind 为 `executable`、`path`、`text`、`secret` 或 `mcp_connection`。这些类型说明值的用途，不意味着宿主已经实现对应设置页面。

配置声明只包含用途和要求；真实程序路径、连接和秘密由使用者配置。它们不属于模型应自行编造的业务参数。`required:false` 的设置可以省略，但不能被调用绑定直接引用而没有其他处理；简单绑定引用的设置必须标为必需。

requirements 是运行条件的说明，不要求能力包都实现安装脚本或就绪检查方法。缺少运行依赖影响当前可用性，不自动使完整声明变成准入不合格。

## 4. 每个操作怎么声明

| 字段 | 是否必填 | 如何填写 |
| --- | --- | --- |
| id | 是 | 包内稳定标识 |
| description | 是 | 操作用途及主要限制 |
| parameters | 是 | 输入参数定义；本地操作用 inline，MCP 可以引用服务定义 |
| invocation | 是 | 明确的调用方式：command 或 mcp |
| result | 是 | 返回内容、成功含义、失败含义及是否只代表受理 |
| effects | 是 | `kind` 为 `read`、`write` 或 `conditional`，并用 `description` 说明实际影响 |

parameters 的两种形式：

- `{"source":"inline","schema":{...}}`：在包内提供标准 JSON Schema，根类型为 object，明确属性、类型、必需项和额外参数规则。采用 JSON Schema 2020-12；此处不另造一套参数类型系统。
- `{"source":"mcp"}`：只用于 MCP 操作，引用 invocation 指定服务中该工具的公开输入定义。服务不可用时应说明定义尚未取得，不能猜参数继续调用。

inline Schema 可使用包内引用，不能依赖没有声明来源的远程文件。Schema 功能支持范围属于后续需明确的表达兼容性问题，不能把“不支持某个关键字”静默当作“该约束不存在”。

### 4.1 脚本和 CLI：command

invocation 包含：

| 字段 | 是否必填 | 含义 |
| --- | --- | --- |
| kind | 是 | 固定为 command |
| program | 是 | `{"setting":"配置键"}`，引用使用者配置的可执行程序；模型参数不能指定任意程序 |
| arguments | 是，可为空数组 | 有序的参数项，见下方约定 |
| stdin | 是 | none 或 json；json 表示向标准输入发送完整业务参数 JSON 后关闭输入 |
| workingDirectory | 否 | `{"setting":"配置键"}`；缺失表示本操作不依赖工作目录，不能隐式假定为项目目录 |
| commandScope | 通用入口必填 | 描述允许的命令范围、限制及参数规则，并在使用说明中给出示例 |

arguments 的元素可以是：

| 表达 | 含义 |
| --- | --- |
| 字符串 | 一个固定参数，例如 `--json` |
| `{"input":"/path"}` | 从业务参数按 JSON Pointer 取一个字符串，作为一个参数 |
| `{"setting":"scriptPath"}` | 从使用者配置取一个字符串，作为一个参数 |
| `{"expand":"/argv"}` | 从业务参数取字符串数组，按原顺序展开成多个参数 |

这四种表达互斥，每个引用对象只能包含对应的一个键。引用不存在、值类型不匹配时，说明本次参数不满足调用约定，不能默默转换成空字符串。需要数值等类型的脚本可以使用 JSON stdin；复杂 CLI 可以由作者提供薄包装脚本。

参数数组直接传给固定程序，不拼接成 shell 命令，也不把参数中的引号、变量或命令替换当成代码求值。此约定不保证被调用程序自身不会执行其他操作；effects 和 commandScope 必须与该程序的实际行为相符。

脚本就是这种调用方式的一种用法：program 指向解释器，arguments 指定脚本路径，业务参数通过 argv 或 JSON stdin 传递。无需因此增加 MCP 包装层。

### 4.2 MCP

invocation 包含：

- `kind:"mcp"`。
- `connection:{"setting":"连接配置键"}`：引用使用者配置的 MCP 连接。
- `tool`：该服务公开的工具名称。

业务参数直接对应远端工具参数，不包含 connection、tool 等安装绑定信息。若 parameters.source=mcp，工具身份和输入定义来自这一处公开声明；不通过文字相似度猜测另一项工具。

如果作者选择 inline，则需确保自己的参数声明与服务实际接受的参数一致。服务不可用或定义不匹配时，应报告当前不可用，不凭旧示例盲目执行。

本文不规定如何实现 MCP 客户端、建立连接或复用进程。

## 5. 返回结果怎么说明

| result 字段 | 是否必填 | 含义 |
| --- | --- | --- |
| format | 是 | json、text 或 mcp；command 使用前两种，mcp 使用 mcp |
| description | 是 | 返回的内容及主要字段含义 |
| successMeaning | 是 | 哪些事实可以据此认定成立，不能仅写“成功了” |
| failureMeaning | 是 | 如何识别失败，失败信息从哪里取得 |
| completion | 是 | `completed`、`accepted` 或 `reported`，见下文 |
| schema | 否 | 可提供结构化业务数据的标准 JSON Schema，加强结果定义 |
| stateDescription | completion=reported 时必填 | 说明从结果哪个字段或明确标记判断完成、受理或失败，列出其含义 |

- completed：成功返回代表这个操作约定的工作已经完成。例如统计操作已经得到统计结果。
- accepted：成功返回只代表请求已被接收或任务已创建。使用说明还需说明后续怎样查询完成情况。
- reported：完成阶段由结果报告。必须写清状态字段/标记；不能仅靠一个成功退出码认定业务完成。

command 的非零退出码表示调用失败，stderr 提供诊断；退出码 0 仅允许进一步按 result 解读业务结果，不自动等同于业务完成。json 格式的 stdout 必须是一个有效 JSON 值，日志放 stderr；text 格式则按公开的文本约定解释。

MCP 的协议错误或工具错误按错误处理，正常返回仍需按 successMeaning/completion 判断业务含义。命令或连接异常也不能证明已经发生的修改被撤回；effects 应帮助主体理解这种影响。

本节约定工具提供者必须把结果说清楚，不设计主体内部的返回包装、状态机或重试机制。

## 6. 使用说明填写提纲

USAGE.md 至少回答以下问题，可以自由组织文章：

1. **适用场景：** 这个能力包解决什么问题，什么情况不适合使用？
2. **前置条件：** 需要哪些依赖和设置，如何准备？
3. **操作流程：** 应选择哪个操作，多个操作如何组合？
4. **输入来源：** 参数从使用者、前一个操作还是运行环境取得？
5. **结果解释：** 成功能证明什么，仅受理之后如何继续，失败如何处理？
6. **行为影响：** 会读取、修改、发送或触发什么？
7. **示例：** 至少一个正常调用及预期结果；通用入口还需给出命令范围示例。

使用说明应引用清单内真实存在的操作名。说明帮助模型选择和组织操作，清单明确实际入口；两处定义冲突时属于声明不一致，应修正后再使用。

## 8. 表达格式的检查边界

通过解析与字段检查，只能证明清单结构和引用自洽；不能证明外部工具真实存在、实现符合说明或当前具备运行条件。

声明试填时检查：顶层注册信息齐全、完整定义入口明确、操作 ID 唯一、配置引用存在、输入映射对应参数、结果含义完整、说明与操作一致。运行前再确认依赖、实际接口和配置。

本格式的机器检查附件见 [capability.schema.json](./capability.schema.json)，检查范围和示例核对见 [准入检查规则与示例核对](./准入检查规则与示例核对.md)。Schema 校验通过不等于全部准入要求或当前运行条件都已核实。当前不进入项目内部系分或解耦实现。
