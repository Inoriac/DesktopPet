## 第三轮 P1 闭环

### stop 后立即 restart + submit

已关闭。

- `ChatPreparationExecutor::start()` 在旧 worker 仍处于 stopping 时记录最新的 pending restart environment，恢复 accepting，并返回成功；不会让 `AIBrain` 进入 running 但 executor 永久不可用的状态。
- 该窗口内的 `submit()` 只保留一个有界 pending request。旧 worker 的结果由 cancellation epoch 抑制；旧线程结束后，pending request 只向新 worker 提交一次。
- `stop_whenRestartIsRequestedDuringShutdown_shouldDispatchPendingRequestOnce` 覆盖 100ms 慢准备后不等待 shutdown，直接执行 `stop -> start -> submit`，断言只收到 pending request 的一个成功结果。该用例单独重复 20 次全部通过。

### restart 后再次 stop

已关闭。

- 每次 `stop()` 都先关闭 accepting、递增 cancellation epoch，并清空 pending restart environment 与 pending request；即使旧 worker 已经处于 stopping，也不会遗漏这一步。
- `finished` 回调只有在 accepting 仍为 true 且 pending restart environment 仍存在时才重启。第二次 stop 清空状态后，回调只回收旧 worker，不会复活线程或派发 pending request。
- `stop_whenPendingRestartIsStoppedAgain_shouldDiscardPendingRequest` 覆盖该时序，断言线程最终停止且结果数为 0。该用例单独重复 20 次全部通过。

## 生命周期与竞态复核

- `m_stopping` 一直保持到旧线程的 `finished` 回调执行 `finalizeStoppedWorker()`，所以外部 `start()` 无法在旧回调之前创建新 worker；旧 `finished` 回调不存在误回收新 worker 的窗口。
- shutdown 在 worker 线程关闭 memory/identity SQLite 资源，再把 Worker 迁回 executor 的 owner thread 并退出 QThread；`finished` 回调随后在 owner thread 删除 Worker。
- 析构调用 `stop()` 清除全部 pending 状态，再等待 queued shutdown 完成。等待返回后由 owner thread 回收 Worker；析构期间排入 executor 的迟到 result/finished 事件会随 QObject 销毁被移除。
- worker task 在执行前、准备后以及 owner-thread emit 前均检查共享 cancellation epoch，并以 `QPointer<ChatPreparationExecutor>` 守护回调。stop、二次 stop 和析构均不会让旧结果越过代际门禁，也未发现 pending request 的 UAF 路径。
- pending request 按值持有，restart 回调先将 pending 状态移入局部变量并清空成员，再启动新 worker 和提交，未发现重复提交或悬空引用。
