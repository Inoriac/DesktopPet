# 设计：聊天发送异步流水线

## 背景与目标

当前桌宠渲染、聊天入口与 `AIBrain::triggerThink` 的发送前准备运行在同一个 Qt GUI 线程。用户提交消息后，运行时快照、事件写入、记忆召回与强化、提示词构建、调用日志和请求序列化会在网络请求真正发出前同步执行，导致渲染定时器短暂得不到调度。

本次目标是在不重构完整 Agent Actor、不改变现有聊天和工具行为的前提下，让展示层在发送消息期间持续流畅，同时尽量保持或缩短模型请求的首包延迟。当前开发环境为 macOS，不以 ONNX 推理或缺失的桌宠 3D 模型作为本地验证条件。

## 方案

采用集中式分阶段异步流水线。`AIBrain` 暂时保留在 GUI 线程，其同步发送入口只负责校验、生成请求标识、更新生命周期状态并提交不可变的准备任务。身份读取、记忆召回、上下文和请求材料构建由单一后台准备执行器处理；准备完成后回到 Qt 网络对象所属线程发起异步模型请求。

读取路径保持纯读取。记忆强化、Event Ledger、调用日志、聊天历史与统计等不影响模型请求正确性的副作用，不再阻塞网络派发，而是进入有序后台持久化队列。所有后台结果携带 `requestId` 与 `generation`，迟到、取消或已被新请求替代的结果不得修改当前回复状态。

方案必须保持现有 `assistantResponseStarted`、stage、delta、finished 生命周期及单条 assistant 消息语义，并为发送到网络派发的各阶段增加轻量耗时观测。性能目标为发送后 16ms 内完成 UI 状态反馈，GUI 线程内单段聊天逻辑不超过 2-4ms，本地准备到网络派发 P95 不超过 50ms。

不采用完整 Agent Actor 的原因是项目功能已基本稳定，后续以缺陷修复和性能调优为主。Actor 化会同时改变 `AIBrain`、Qt 定时器、网络对象、SQLite 连接、工具回调和退出清理的线程归属，回归风险与开发成本显著高于当前收益。

实现仍按 Actor 兼容的消息边界组织：后台任务仅接收不可变输入并返回值对象，不直接操作 GUI 或 `AIBrain` 可变状态。若未来性能分析显示多个 AI 子系统持续阻塞、需要并行处理多轮请求，或重新大规模扩展视觉、语音和工具能力，再将这些消息边界迁移为完整 Agent Actor。

## 澄清结论

- [2026-09-02] 当前采用集中式分阶段异步流水线，不立即重构完整 Agent Actor。
- [2026-09-02] 优先保证展示层无卡顿，同时避免把非关键持久化放在模型请求关键路径上。
- [2026-09-02] 异步任务按 Actor 兼容的不可变消息与 generation 门禁设计，保留未来迁移能力。
- [2026-09-02] README 需要记录当前方案、性能边界和升级完整 Agent Actor 的触发条件。
- [2026-09-02] macOS 本地不运行 ONNX，也不启动依赖缺失 3D 模型资源的完整桌宠。
